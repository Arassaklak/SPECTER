# SPECTER — Security model

## Threat model

**Protects against** a passive or active attacker on your LAN / Wi-Fi (another device,
a rogue AP, ARP spoofing): they cannot read the screen stream, inject input, recover
your password, replay captured frames, or MITM the session.

**Does not protect against** a compromised endpoint (malware already on the PC or the
phone), someone who knows your password, or physical access to an unlocked device.
Those are outside what a transport can fix.

## 1. Password handling

- The password is **never sent**, not even hashed-and-sent.
- It is stretched with **PBKDF2-HMAC-SHA256, 210,000 iterations**, into a 32-byte
  *master key*. A random 16-byte salt is generated by the server per connection and
  sent in the clear (salts are not secret). Same salt → both sides derive the same
  master key.
- On the phone the password is optionally stored in the **iOS Keychain**
  (`kSecAttrAccessibleWhenUnlockedThisDeviceOnly`), never in UserDefaults/plist.
- On the PC it is entered at launch (or read from the `SPECTER_PASSWORD` env var for
  headless starts) and **never written to disk**.

## 2. Authenticated handshake with forward secrecy

```
server → client : "SPECTR" ver salt(16) s_nonce(16) s_eph_pub(32)
client → server : c_nonce(16) c_eph_pub(32) c_proof(32)
server → client : s_proof(32)

transcript = salt ‖ s_nonce ‖ s_eph_pub ‖ c_nonce ‖ c_eph_pub
master     = PBKDF2(password, salt)
c_proof    = HMAC-SHA256(master, transcript ‖ "SPECTER-c2s")   # client → server auth
s_proof    = HMAC-SHA256(master, transcript ‖ "SPECTER-s2c")   # server → client auth
shared     = X25519(own_eph_priv, peer_eph_pub)
sessionKeys= HKDF-SHA256(ikm = shared, salt = transcript, info = per-direction label)
```

Why this is strong:

- **Mutual authentication.** Each side must produce an HMAC over the *entire*
  transcript (including both ephemeral public keys) using the password-derived master
  key. An attacker without the password cannot forge either proof, so they cannot
  impersonate the server *or* the client, and cannot tamper with the ephemeral keys
  undetected → **no man-in-the-middle**.
- **Forward secrecy.** The session keys come from an **ephemeral X25519** exchange, not
  from the password. The ephemeral private keys live only in RAM for the life of the
  connection. Capturing the ciphertext today and learning the password later yields
  nothing, because the attacker never had the ephemeral secrets.
- **Wrong password fails closed.** The server compares proofs in constant time and just
  drops the connection on mismatch — it never reveals whether it was a bad password or
  tampering.

## 3. Record layer — AES-256-GCM

Every post-handshake message:

```
wire = length(4) ‖ counter(8) ‖ AES-256-GCM_ciphertext ‖ tag(16)
nonce = direction_prefix(4) ‖ counter(8)          # 12-byte GCM nonce, unique per frame
```

- **Confidentiality + integrity**: GCM authenticates every byte; any bit-flip makes
  decryption fail and the session aborts.
- **Unique nonces**: a monotonic 64-bit counter per direction, combined with a
  per-direction random prefix derived from the handshake. Counters never repeat within
  a session, so **GCM nonce reuse is impossible**.
- **Replay / reorder protection**: the receiver requires the counter to match its
  expected next value; a replayed or reordered frame is rejected.
- **Separate keys per direction** (client→server vs server→client) so the two streams
  can never be crossed or reflected.

## 4. Operational hardening

- `allow_only_ip` in `config.json` restricts connections to a single client IP.
- One session at a time; additional connections wait in the accept backlog.
- The server injects input via the logged-in user's session only; it grants no
  privilege it doesn't already have.
- Windows Firewall: allow SPECTER on **Private** networks only, never Public.

## 5. Reaching it from outside the LAN (do this the safe way)

SPECTER is LAN-only on purpose. **Do not** port-forward 45813 to the internet. If you
need remote access from outside, run a **WireGuard** VPN back to your home network and
connect SPECTER to the PC's LAN IP through the tunnel. You then get WireGuard's modern
crypto on the outside *and* SPECTER's AES-256-GCM on the inside — defense in depth,
and nothing about your PC is exposed to the public internet.

## 6. Cryptographic dependencies

- PC: the [`cryptography`](https://cryptography.io) library (OpenSSL-backed) for
  PBKDF2, X25519, HKDF, HMAC and AES-GCM.
- iOS: Apple **CryptoKit** (X25519, HKDF, HMAC, AES-GCM) and **CommonCrypto** (PBKDF2).

Both implement the same standards (RFC 5869 HKDF, RFC 7748 X25519, NIST AES-GCM), so
the two ends interoperate byte-for-byte.
